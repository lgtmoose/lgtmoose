# Security policy

## Reporting a vulnerability

Report vulnerabilities privately through GitHub's **Report a vulnerability** button on this repository's Security tab. Please don't open a public issue, PR or discussion about it.

> The button only appears once the repository's owner turns on **private vulnerability reporting** (Settings → Code security → Private vulnerability reporting). Until it's on, open a minimal public issue asking a maintainer to get in touch, without any detail of the problem.

What to include: the affected version or commit, the component (gateway, control task, sandbox, Lambdas, CLI), steps to reproduce, and what an attacker gains. A proof of concept against your own install is welcome. Please don't test against installs you don't run.

What happens next:

| Step                                                    | Target                    |
| ------------------------------------------------------- | ------------------------- |
| We acknowledge the report                               | 3 working days            |
| We confirm or rule out the issue, with a severity       | 10 working days           |
| A fix or mitigation for a critical or high issue        | 30 days from confirmation |
| A fix for a medium or low issue                         | the next release          |
| Public advisory (GitHub Security Advisory, with credit) | once a fix is released    |

We'll keep you updated in the advisory's private thread and agree a disclosure date with you. LGTMoose is self-hosted, so operators apply fixes themselves: an advisory says what to upgrade and whether a redeploy is needed.

### In scope

- Prompt injection that changes a review's decision, approves a PR, clears a blocking finding, or writes a learning.
- Any path by which the model sandbox can reach GitHub, read GitHub, database or other providers' credentials, or reach hosts outside its egress allowlist.
- Webhook spoofing, or replay that does more than re-run a review.
- Data from one repository, installation or org reaching another.
- Credentials or personal data leaking into logs, transcripts, comments, learnings or the database.
- A permission check that can be skipped: commands, declines, resolving threads, learnings.
- Escaping bugs that let PR text post mentions, links or markup through LGTMoose's comments.

### Out of scope

- What a model says or misses inside an untouched, honest review (a wrong or missing finding): report those as ordinary issues.
- Findings that need control of the AWS account, the GitHub App's private key, or the operator's machine.
- Denial of service through volume (many PRs or comments): GitHub's and AWS's limits apply.
- Issues in the vendor CLIs or model APIs themselves: report those to the vendor.

## Threat model

LGTMoose reads untrusted content (pull requests, comments, code) with a model, and holds credentials that can write to GitHub. The design rests on one rule: **the model only reads and returns JSON; plain code holds every credential and makes every decision.** See [Architecture](docs/architecture.md) for the components.

### Assets

| Asset                                                       | Where it lives                                         |
| ----------------------------------------------------------- | ------------------------------------------------------ |
| GitHub App private key                                      | Secrets Manager `lgtmoose/github-app`                  |
| Webhook secret                                              | Secrets Manager `lgtmoose/github-webhook-secret`       |
| Model credentials (one per provider)                        | Secrets Manager `lgtmoose/provider/<id>`               |
| Linear API key (ticket coverage, optional)                  | Secrets Manager `lgtmoose/tickets/linear`              |
| The App's OAuth client (dashboard sign-in)                  | Secrets Manager `lgtmoose/github-app-oauth`            |
| Dashboard sessions                                          | RDS `dashboard_sessions` (token hashes only)           |
| Database credentials, findings, learnings                   | RDS (Secrets Manager for the credentials)              |
| Source code of the reviewed repositories                    | Control task's clone; the sandbox's read-only checkout |
| Run artifacts and transcripts                               | The S3 artifact bucket                                 |
| The review decision (approve / request changes / check run) | GitHub, written only by the control task               |

### Trust boundaries

1. **GitHub → gateway.** Anyone can send a request to the webhook URL.
2. **PR content → the model.** The PR's title, body, comments and code are written by whoever opened or commented on the PR, which on a public repository is anyone.
3. **Model output → plain code.** Findings, notes and judgements are model output, so treated as untrusted data.
4. **Sandbox → network.** The process running the model may be steered, so it's boxed in.
5. **Repository config → review.** `.lgtmoose.yaml`, rule packs and conventions are read from the base branch, so a PR can't change how it's reviewed.
6. **GitHub users → commands and learnings.** Who someone is and what access they have comes from GitHub, never from what they write.
7. **Browser → dashboard.** Anyone can open the dashboard's URL; only members of `allowedOrgs` get a session, and only for the repositories they can see.

### The prompt-injection detector

Plain code, no model, in `packages/pipeline/src/injection.ts`. It runs in the post step over what the reviewer read:

- **Added lines.** A line the PR adds that holds text aimed at an AI reviewer, chat-format markup, text that tries to open or close an `<untrusted>` block, bidirectional control characters (Trojan Source), Unicode tag characters, or a run of zero-width characters, gets a blocking `prompt_injection` finding on that line. It's posted and tracked like any finding: it goes when the line goes, and only someone other than the PR's author with write access can resolve or decline it. At most 10 per run.
- **Title, description and comments.** The same checks, plus directives hidden in HTML comments, hold approval for the run: LGTMoose posts a comment and a check that asks a person to look, and the summary says where. It's worked out again each run, so editing the text away clears it. Text by the repository's owners, members and collaborators, and by bots, isn't scanned here: they can approve the PR anyway.
- **Linked tickets.** With ticket coverage on, the same checks run over each linked ticket's text (title, description, comments, parent and sub-issues), whoever wrote it. A hit holds approval for the run, and the summary names the ticket.
- **Allowed files.** `injection.allow` in `.lgtmoose.yaml` (from the base branch) lists globs whose added lines aren't scanned, for tests and docs about prompt injection. Their contents still reach the reviewer.

It's tuned for few false positives: it looks for phrases addressed to an AI ("ignore previous instructions", a named model or reviewer told to approve or not report), not for words like "ignore" or "approve" on their own. `packages/evals/fixtures/injected-approval` checks it end to end.

### Residual risks

What these controls don't cover, and what's left as a known limit:

- **Injection that evades the detector.** The detector matches patterns, so a paraphrase, another language or an instruction spread across lines can get past it. If that also convinces the reviewer to report nothing, the review can approve. Keep a required human approval on protected branches (see [Providers](docs/providers.md)): LGTMoose's approval should be a signal, not the only gate.
- **Allowed files and trusted authors.** Files under `injection.allow` aren't scanned, and neither is text by owners, members and collaborators. Keep the globs narrow.
- **Holding approval is open to outsiders.** A drive-by comment with injection text holds approval on a PR until it's edited or deleted. It can't approve or clear anything.
- **Model vendors see the code.** The sandbox sends the code under review to the configured model APIs; that's the point. Choose vendors and plans whose terms suit your code ([Providers](docs/providers.md)).
- **GitHub Enterprise Server** on its own domain isn't recognised by the `extraEgressHosts` check. Don't list it there.
- **Thread resolutions by the webhook** for blocking findings wait for the next run, which checks the resolver's access: the dispatcher holds no GitHub credential.
- **Pending learnings** can be proposed by anyone who can comment, up to `learnings.maxPendingPerAuthor` (5 by default) per author in an org; they have no effect until someone with access approves them, on a PR (`approve <id>`) or on the dashboard.
- **A bootstrap reads write-access authors' current access**, not their access when the PR merged (GitHub doesn't keep it), and its proposals can be wrong about the team's taste: that's why each one waits for a person, with links to the comments it rests on.
- **A claimed fix on a file this run didn't review** stays open until the file changes again or a person resolves the thread.
- **One install per AWS account and region.** Secrets have fixed names, so a second install there overwrites the first one's App credentials (NIC-852).
- **The Cursor CLI** is installed only when a provider uses it, and only with a recorded checksum unless the operator explicitly allows an unverified download.
- **Dashboard access** is fixed at sign-in for up to 8 hours: someone removed from the org, or from a repository, keeps what their session shows until it ends. The same holds for approving and rejecting learnings: write access or org ownership taken away on GitHub still counts on the dashboard until the session ends, since the dashboard records it at sign-in rather than asking GitHub (with the App's key) on each change. Anyone with an active session sees every open finding in the repositories they can see, including findings' text. The dashboard's API Gateway URL is also reachable directly, but browsers never send the session cookie there.
- **Image scans** build for the CI runner's architecture; deploys build arm64 from the same Dockerfiles and pinned base images. An architecture-specific package could differ.
